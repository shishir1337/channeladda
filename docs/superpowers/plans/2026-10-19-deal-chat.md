# Deal Chat Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Buyers, sellers and the assigned agent can negotiate and run a whole deal from the conversation, while every existing page keeps working.

**Architecture:** Every offer and deal change writes a `Message` row of kind OFFER or EVENT into the deal's conversation, inside the change's own transaction, from the server function that makes the change — so the timeline is the same whichever page acted. One pure function (`dealPanelState`) decides the single "what can I do now" panel per viewer; the panel reuses the existing `StartDeal`, `PayNow`, `DealNextStep`, `RaiseDispute` and offer-card buttons. A 5-second fingerprint poll keeps an open conversation current.

**Tech Stack:** Next.js 16.4 (App Router, Turbopack), React 19.3, TypeScript 7, Prisma 7.10 + adapter-pg, Better Auth 1.7, Vitest 5, Biome 2.5, pnpm 11.

**Spec:** `docs/superpowers/specs/2026-10-18-deal-chat-design.md`

## Review Focus

1. **Events with no sender reaching code that assumes one.** `listThreads`, `listStaffThreads`, the admin user page's thread count, dispute counts and previews must all handle a system event (sender null). Test: Task 6, `"every thread reader copes with a system event"`.
2. **A conversation created at the same moment by "Ask the seller" and an offer or a deal.** One thread, no 500. Test: Task 2, `"two writers creating the same conversation end with one"`.
3. **Someone who loses access while the page is open.** The fingerprint route answers 404 and the client stops polling. Test: Task 5, `"a stranger gets no fingerprint"`, and Task 14, `"an agent whose deal ended gets no fingerprint"`.
4. **An offer note that is nothing but contact details** stores only the marker and flags the thread. Test: Task 3, `"a note that is only a phone number is stored as the marker"`.
5. **A buyer whose earlier deal in the same conversation ended** sees "buy" when the listing is back on sale and "unavailable" when someone else holds it. Test: Task 8, rows `lapsed-deal-listing-live` and `lapsed-deal-listing-reserved`.

  ```ts
    | { kind: "unavailable"; listingStatus: ListingStatus };
  export function dealPanelState(input: PanelInput): PanelState;
  ```
- The precedence, which the tests pin (the first rule that matches wins):
  1. `staff` viewer → `staff`.
  2. The deal is running (not terminal):
     - AWAITING_PAYMENT → `pay` for the buyer, `waiting-for-payment` for everyone else;
     - otherwise `step`, where `yourMove` = status not DISPUTED, `holdUntil` null or `<= now`, and `nextStep.actor === viewer`. This is the same rule as `mine` in `DealNextStep`.
  3. `agent` viewer → `finished` if there is a deal, else `unavailable`.
  4. `heldOffer` → `start-deal` for the buyer, `waiting-to-start` for the seller.
  5. `latestOffer` effectively OPEN → `offer-your-turn` when its `awaiting` (bySeller → buyer, else seller) is the viewer, else `offer-waiting-on-them`.
  6. Listing LIVE → `buy` for the buyer, `propose` for the seller.
  7. The deal is COMPLETED → `finished`.
  8. Otherwise → `unavailable`.
